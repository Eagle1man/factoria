## 2. Границы доверия

| Слой | Доверие | Что может | Что не может |
|---|---|---|---|
| LLM (DeepSeek) | **не доверенный** | предлагать команды через 8 инструментов | писать в ПЛК, читать теги напрямую, отменять валидацию |
| Backend | доверенный | валидировать, исполнять, писать аудит | обходить interlocks эмулятора |
| Эмулятор OPC UA | доверенный (в dev) | отклонять запись по физике, автостоп | исполнять приказ «через силу» |
| 1С | источник факта | отдавать заказы | получать запись (v1) |
| UI | не доверенный | показывать, инициировать approve/reject от имени пользователя из JWT | писать в теги, подменять `operator_id` |
| FUXA | **исключена из v1** | — | обходить валидатор |

## 3. Карта зависимостей по этапам

```text
этап 1  opcua-emulator ──────────────┐
этап 2  backend: config, auth,        │  (WS/кэш читают теги эмулятора)
        registry, opcua/client,      ◄┘
        realtime, api, storage
этап 3  frontend (3D + 2D)  ◄── WS этапа 2
этап 4a adapters/stub + validation 1–3 ◄── этап 2 (кэш, БД)
этап 4b adapters/http_ones + BSL       ◄── доступ к 1С (внешняя зависимость)
этап 5  agents/ (LangGraph)            ◄── API 4a + ключ DeepSeek (внешняя)
этап 6  validation 4–5 + пульт         ◄── 5 (кто предлагает) + 4 (что валидировать)
этап 7  strategies supervisor/debate   ◄── 5, 6
этап 8  simulator/satisfactory         ◄── 7 (включать после)
```

Критический путь: 1 → 2 → 4a → 5 → 6 → 7. Этап 3 параллелен 4a, этап 4b
независим и упирается только в доступ к 1С.

## 4. Дублирование, которое нужно снять явно

| Пара | Проблема | Решение |
|---|---|---|
| Файловый мост 1С (старый) и HTTP-сервисы (новый) | два способа получить один заказ, разные форматы | в `factoria/` только адаптер; мост — fallback демо (ADR-107) |
| RapidSCADA (`scada_client`) и OPC UA-эмулятор | два источника телеметрии | v1 — эмулятор; SCADA подключается как второй адаптер после пилота |
| `platform/` старого репо и `backend/` нового | часть идей (core, llm router) пересекается | старый `platform/` замораживается, не развивается |
| Lovable-UI и старый `panel_server` | UI сделан под `/api/*`, новый backend — `/api/v1/*` | ADR-106: UI переводится на `/api/v1` |
| `docs/specification.md` и `TZ.md` старого репо | два разных ТЗ в двух репозиториях | источник истины для `factoria/` — только `docs/specification.md` |

## 5. Пробелы архитектуры ТЗ

1. **Нет `tests/` и `scripts/` в дереве §2**, хотя §11 и §8.2 на них ссылаются.
   Созданы в `factoria/` (пустые).
2. **Нет схемы `registry.yaml`** — заполнено в `docs/tag-registry.md`.
3. **API не покрывает 2D-панель** — 7 путей помечены PLANNED в `docs/api.md`.
4. **Нет хранилища пользователей** для `/auth/login` — добавлено в `docs/data-model.md`.
5. **`tag_history` без ретенции** — добавлен `TAG_HISTORY_RETENTION_H`.
6. **`q=BAD` при обрыве OPC UA ≤3 c** требует явных параметров подписки
   (`publishing_interval`, `max_age`), иначе DoD этапа 2 недостижим.

## 6. Что проверено фактически (не по документам)

- `asyncua 2.1.0` на Python 3.14.3: сервер + клиент + method-нода + interlock —
  **работает**, см. `scripts/spike_opcua_methods.py` и `technology-stack.md`.
- `writable=False` действительно блокирует клиента (`BadUserAccessDenied`),
  а method-нода пишет на сервере — то есть паттерн §4.3 ТЗ исполним.
- `alembic 1.20.1` и `langgraph 1.2.19` ставятся на 3.14; `SqliteSaver`
  требует отдельный пакет `langgraph-checkpoint-sqlite`.
