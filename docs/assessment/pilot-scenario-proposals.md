# PILOT-SCENARIO-PROPOSALS.md — 5 сценариев пилота

Дата: 2026-11-05. Не утверждены. Сложность: S — 1–2 дня, M — 3–5, L — 6+.
Все сценарии используют только эмулятор и stub-1С; реальный контур не затрагивается.

## S1. «Перегрев» — проверка физической защиты (S)

| | |
|---|---|
| **Цель** | доказать, что LLM не может обойти interlock |
| **Ход** | оператор поднимает Temp.PV L1 выше 80; агент `production` просит `set_setpoint=600` |
| **Ожидание** | backend отклоняет на `interlock_check` **или** эмулятор возвращает `BadInvalidState`; в аудите — `INTERLOCK_001` |
| **Доказывает** | §4.3, §6.1 стадия 3, §13 «LLM без транспорта к ПЛК» |
| **Зависит** | этап 1 (эмулятор) + 4a |
| **Риск** | если отказ произойдёт только на эмуляторе, а backend пропустит — это дефект: нужны **оба** уровня |

## S2. «Срочный заказ» — supervisor (M)

| | |
|---|---|
| **Цель** | показать планирование при дефиците времени |
| **Ход** | в stub появляется заказ с `due_date` через 2 часа; L2 загружена 96%, L3 свободна |
| **Ожидание** | `supervisor` выбирает стратегию, предлагает `reallocate_job` на L3 → A1 → подтверждение → `REVALIDATING` → `EXECUTED` |
| **Доказывает** | §7.3, §7.5, §5.1 (полный путь A1) |
| **Зависит** | этапы 4a, 5, 6 |
| **Риск** | заказ нужно «оживить» в stub; без `POST /debug/orders` сценарий не воспроизводим |

## S3. «Перегруз L2» — debate (M)

| | |
|---|---|
| **Цель** | показать разрешение конфликта ролей без усреднения |
| **Ход** | Load.Pct L2 > 95 дольше 60 c → автостоп L2; production хочет `switch_recipe R4` (быстрее), logistics — `reallocate_job` на L1 |
| **Ожидание** | debate 2–3 раунда; ничья → consensus 3 роли; повторная ничья → эскалация A1 человеку |
| **Доказывает** | §7.5 (жюри, ничья, эскалация), §7.8 DoD |
| **Зависит** | этап 7 |
| **Риск** | при 2 голосах ничья вероятна (~50%) — сценарий будет часто уходить человеку; см. OD-08 |

## S4. «Ночная смена» — автономия A2 (M)

| | |
|---|---|
| **Цель** | доказать, что A2 работает **только** в коридоре и всегда пишет аудит |
| **Ход** | серия шагов уставки: 380→420→400→450 при Temp 70 и Load 60 |
| **Ожидание** | 380→420 (Δ40, new>400) → **A1**; 420→400 → **A2** (уведомление, аудит); 400→450 → **A1**; при Temp 85 любая команда → **отказ** |
| **Доказывает** | §6.4 (все 6 условий), §6.5, ADR-103 (флаг `AUTONOMY_MAX`) |
| **Зависит** | этап 6 |
| **Риск** | граница 400 rpm — самая ошибкоопасная; нужны тесты 399/400/401 |

## S5. «Просроченный approve» — TTL и ревалидация (S)

| | |
|---|---|
| **Цель** | доказать, что подтверждение не «зависает» и не исполняется вслепую |
| **Ход** | A1-команда уходит в `AWAITING_APPROVAL`; (а) оператор не реагирует 5 мин; (б) оператор подтверждает, но за это время Temp вырос до 85 |
| **Ожидание** | (а) `EXPIRED`; (б) `REJECTED_AT_REVALIDATION`, оператор уведомлён, в аудите причина |
| **Доказывает** | §5.1, §6.6, §6.7 DoD |
| **Зависит** | этап 6 |
| **Риск** | TTL надо проверять с управляемыми часами (freezegun), иначе тест идёт 5 минут |

## Сравнение

| Сценарий | Сложность | Этапы | Что доказывает бизнесу |
|---|---|---|---|
| S1 Перегрев | S | 1, 4a | «ИИ не может сломать оборудование» |
| S2 Срочный заказ | M | 4a, 5, 6 | «ИИ ускоряет планирование» |
| S3 Перегруз | M | 7 | «конфликт ролей решается прозрачно» |
| S4 Ночная смена | M | 6 | «автономия строго в коридоре» |
| S5 Просроченный approve | S | 6 | «человек остаётся в контуре» |

**Рекомендация для первого показа:** S1 → S5 → S4 (все на этапе 6, не требуют
DeepSeek и внешней сети). S2 и S3 — после этапа 7, когда появится агентная часть.
Если ключа DeepSeek не будет, S1/S4/S5 всё равно демонстрируют систему целиком,
кроме «интеллекта» — это честная деградация, а не имитация.
